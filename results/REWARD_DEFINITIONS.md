# Reward and step-correctness definitions — `outcome_reward`, `process_reward`, `step_correct`

> **What this document is.** A self-contained, code-grounded explanation of
> the four reward / correctness signals every other doc in `results/` and
> the research log refer to. Every definition cites the exact source file
> and function. Read this once if any of `outcome_reward`,
> `process_reward`, `step_correct`, or "gold graph" are unclear.

## 0. The synthetic dataset and where the gold graph comes from

Every problem in `data/composition_hf/test_small/op{op}-{N}.jsonl` is
generated by a templated graph-of-quantities sampler (see `DATASET.md`
for the recipe). Each problem ships with three fields:

- `problem` — the natural-language question setup.
- `question` — the actual question to answer ("What is the total
  number of …?").
- `solution` — the canonical step-by-step gold trace, formatted as a
  sequence of `Define <name> as <symbol>; so <symbol> = <expr> = … = <int>.`
  lines, ending with `Answer: <int>.`. The integers along the trace
  are computed deterministically from the sampler's parameters.

The "gold graph" is a directed graph whose nodes are the named
quantities (`var_name`s, e.g. `"intense detective thriller in West
Sahara Movie Festival"`) and whose edges encode the dependencies
implied by the equations. The graph is parsed from the `solution`
string by `utils.solution_dependency_graph.parse_graph` (see
`utils/solution_dependency_graph.py`). For each node we know:

- its `name` (the descriptive English `var_name`)
- its `value` (the integer the gold solution assigns to it)
- its `dependencies` (which other nodes its expression references)

The gold graph is the source of truth for both `process_reward` and
`step_correct`. It exists in this sandbox because the data is
synthetic — on a real benchmark like GSM8K or MATH-500 there is no
gold graph for free, which is the central "does this scale?"
question for the proxy programme.

## 1. `outcome_reward` — binary final-answer correctness

**Source:** `verl/reward_fn.py::_structural_score` (lines ~327-333) and
`verl/reward_fn.py::_compute_step_process_reward` (lines ~82-84).

**Computation:** the rollout's predicted final answer (extracted from the
`<answer> ... </answer>` tags by `extract_answer`) is normalised
(strip, integer-coerce) and compared to the gold answer
(`ground_truth["answer"]`):

```python
outcome_reward = 1.0 if normalise(predicted_answer) == normalise(gold_answer) else 0.0
```

This is the **standard RLVR reward** — what GRPO sees by default at
training time when `compute_score = compute_score_with_step_process` is
configured to use the binary outcome variant, and what every
`outcome_mean@128` evaluation reports.

It is **the cleanest deployable signal** (no gold trace required, just
a final-answer checker), and Phase 1c established that it is also the
*only* per-rollout signal whose within-prompt ρ with `process_reward`
is meaningfully > 0 (wp ρ +0.86 — mechanically, since
`outcome_reward=1 ⇒ process_reward=1` once the trace is graph-faithful).

## 2. `process_reward` — continuous graph-faithfulness in [0, 1]

**Source:** `verl/reward_fn.py::_structural_score` (lines ~334-373).

**Computation:** the rollout text is parsed into a predicted graph by
`parse_graph(solution_str)`. The predicted graph is compared against the
gold graph by `gold_graph.compare(pred_graph, value_tolerance=1e-6)`, which
returns a structural diff with four kinds of mismatch:

| field                | meaning                                                                                       |
|----------------------|-----------------------------------------------------------------------------------------------|
| `value_mismatches`   | nodes the rollout defined but with the wrong integer value                                    |
| `dependency_mismatches` | nodes the rollout defined but with the wrong set of parent nodes (wrong dependency edges) |
| `missing_in_pred`    | gold nodes the rollout never defined (skipped quantities)                                     |
| `extra_in_pred`      | nodes the rollout defined that aren't in the gold graph (hallucinations)                      |
| `answer_mismatch`    | a single bool flag for whether the final answer is wrong                                      |

The penalty is

```python
penalty = (
    n_value_mismatch
    + n_dep_mismatch
    + n_missing_in_pred
    + (1 if answer_mismatch else 0)
)
process_reward = max(0.0, 1.0 - penalty / max(n_gold_nodes, 1))
```

Note: `extra_in_pred` (hallucinated nodes that aren't in the gold graph)
does NOT enter the penalty. We deliberately do NOT punish writing
extra Define lines, because doing so would let the model game the
metric by being terse.

`process_reward ∈ [0, 1]` continuously: 1.0 is a fully graph-faithful
trace with the right answer, 0.0 is a complete mess. A trace that has
all the right intermediate quantities but a wrong final answer scores
~0.9 (one penalty unit out of `n_gold` nodes).

`process_reward` is the **oracle signal** Phase 1 / 1b / 1c are
trying to recover from rollouts. It is sandbox-only because building
the comparison graph requires the `solution` field that GSM-Infinity
provides for free but GSM8K / MATH does not.

## 3. `outcome_reward` vs `process_reward` — what the gap tells us

| outcome | process | reading                                                                                        |
|--------:|--------:|------------------------------------------------------------------------------------------------|
| 1.0     | 1.0     | clean solve: right answer AND graph-faithful trace.                                            |
| 0.0     | ~0.9    | "almost-solver": graph-faithful trace, wrong final answer (arithmetic / equation-solver bug).  |
| 1.0     | ~0.4    | answer-only correct: the trace skips most gold quantities but happens to land on the right number ("guesser"). |
| 0.0     | 0.0     | nothing useful in either trace or answer.                                                      |

The `process_reward − outcome_reward` per-(run × op) gap is what
`results/phase1_findings.md §Per-(run × op) outcome / process tables`
tabulates. A positive gap on hard ops means the model knows the structure
but can't carry the arithmetic; a negative gap means it's guessing.

## 4. `step_correct` — per-`Define`-line gold-correctness

**Source:** `scripts/gsm_infinity_rl/compute_phase1c.py::compute_signals`
(lines ~436-452) and the schema in `define_steps.jsonl`:

```python
step_correct = int(
    pred_val is not None
    and gold_val is not None
    and pred_val == gold_val
)
```

For each `Define X = K` line the rollout writes:

1. `pred_val` = the integer the rollout assigned to `X`. Comes from
   `SolutionParser.parse(rollout_text).steps[i].value`. May be `None` if
   the line is unparseable or if the value is symbolic (e.g. `8*x + 1`
   with `x` not yet pinned).
2. `gold_val` = the integer the gold graph assigns to the same
   `var_name X`. Comes from `gold_value_map(gold_solution, parser)`,
   keyed by the (normalised) descriptive name of the variable. May be
   `None` if `X` is not in the gold graph at all (a hallucinated
   variable name).
3. `step_correct = 1` iff both are non-None and they match. `step_correct
   = 0` otherwise (whether the line was unparseable, hallucinated, or
   simply wrong).

Two consequences of this construction that matter throughout the docs:

- **80%+ of Define lines on hard ops have `gold_value=None`** (the
  rollout names a variable not in the gold graph). These get
  `step_correct=0` mechanically, which inflates any pooled rho between
  a per-step signal and `step_correct`. This is why phase1c § Finding 2
  insists every per-step rho be reported on the **gold-grounded**
  subset (records with `gold_value` not None) — that's the only
  filter that asks "given the model is talking about a real
  quantity, is its value right?"
- `step_correct` is **stricter than process_reward**. A rollout can
  achieve `process_reward = 1.0` even with one wrong intermediate
  Define line if the line is `extra_in_pred` (hallucinated extra
  node not in the gold graph) — because `extra_in_pred` is not
  penalised. So a rollout's `step_correct` average across its lines
  is typically lower than its `process_reward`. The two signals are
  related but not identical.

## 5. The "outcome class" / "structural zero variance" classification

**Source:** every per-prompt outcome distribution table, e.g.
`phase1c_findings.md §D` and `phase1e_consensus_findings.md`.

For each prompt with K=16 sibling rollouts, classify by the count of
`outcome_reward = 1` siblings:

| class         | siblings correct | what GRPO sees                                                                |
|---------------|------------------|-------------------------------------------------------------------------------|
| `allcorrect`  | 16/16            | within-prompt advantage = 0 for every sibling (mean=1, A_i = r_i − 1 = 0 ∀i). |
| `mixed`       | 1..15            | within-prompt advantage is non-zero for at least one sibling. **The only regime GRPO has gradient on.** |
| `allwrong`    | 0/16             | within-prompt advantage = 0 for every sibling (mean=0, A_i = 0 − 0 = 0 ∀i).   |

The "structural zero-variance bottleneck" is that on hard ops at our
model scale (`grpo_edge_v4 @ 388`), 44% of op17 prompts and 68% of
op19/20 prompts are `allwrong`. So even a perfect process oracle
**cannot extract gradient on the all-wrong cell** — there is nothing
to amplify within-prompt. Per-rollout within-prompt shaping methods
are mechanically ceiling-bounded at the remaining 24-44% of
`mixed`-outcome prompts on those ops.

The `mixed`-only subset is also the cleanest within-prompt
difficulty control for the "consensus correlates with correctness"
question (Q1 sanity check in `phase1e_consensus_findings.md`).

| signal              | granularity | source                                          | ground-truth required? | range / type | used in                                                                                  |
|---------------------|-------------|-------------------------------------------------|------------------------|--------------|------------------------------------------------------------------------------------------|

| `outcome class`     | per-prompt  | downstream of `outcome_reward`                  | as `outcome_reward`    | {AC, mixed, AW} | structural-zero-variance analyses; `mixed`-only sanity checks.                            |
